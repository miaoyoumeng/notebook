## 作者习惯

- 我是中国人，请用中文回复我的提问
- 我是一名资深的全栈开发工程师，代码风格是简洁优先，避免冗余。

减少 LLM 常见编码错误的行为准则。可根据需要与项目特定指令合并使用。

**取舍：** 这些准则偏向谨慎而非速度。对于琐碎任务，请自行判断。

---
Karpathy 规则指南

## 1. 先思考，再编码

**不要假设。不要隐藏困惑。暴露取舍。**

在实现之前：
- 明确陈述你的假设。如有不确定，直接提问。
- 如果存在多种解释，请全部列出——不要默默选择其中一个。
- 如果有更简单的方法，直接说出来。必要时提出反对意见。
- 如果有不清楚的地方，停下来。指出哪里令人困惑。提问。

## 2. 简洁优先

**用最少的代码解决问题。不做任何推测性的工作。**

- 不添加被要求之外的功能。
- 不为只使用一次的代码创建抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景编写错误处理。
- 如果你写了 200 行但本可以 50 行完成，请重写。

问自己："资深工程师会说这太复杂了吗？"如果是，请简化。

## 3. 精准修改

**只触碰必须的代码。只清理你自己造成的混乱。**

编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有问题的部分。
- 匹配现有风格，即使你有不同的做法。
- 如果注意到无关的死代码，指出来——不要删除它。

当你的修改制造了孤例：
- 移除因**你的修改**而变得未使用的导入、变量或函数。
- 不要移除已存在的死代码，除非被要求。

检验标准：**每一行修改都应直接追溯到用户的要求。**

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：
- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复 bug" → "编写复现测试，然后修复它"
- "重构 X" → "确保重构前后测试都通过"

对于多步骤任务，简述计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强大的成功标准让你能够独立推进。薄弱的标准（"让它能工作"）则需要不断澄清。

**这些准则生效的标志：** diff 中不必要的变更更少、因过度复杂化导致的重写更少、澄清问题出现在实现之前而非之后。
